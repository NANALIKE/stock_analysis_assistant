# 产品需求

按产品能力组织当前需求基线，按可独立评审和交付的用户目标记录需求变更。能力主文档持续维护，变更文档保留本次交付的范围、原因和验收标准。

## 能力索引

| 产品能力 | 阶段与状态 | 当前需求基线 | 需求变更 |
|---|---|---|---|
| 行情数据 | 技术一期；已实现手动日更、历史补采与查询，验收范围见能力文档 | [行情数据](market-data/README.md) | [变更索引](market-data/changes/README.md) |

公司事实、股票分析、评估和问答等后续能力，在开始定义需求时再创建目录；阶段边界以[产品架构](../architecture/product-architecture.md)为准。

## 目录约定

```text
docs/product/
├── README.md                    # 能力、阶段与文档索引
└── market-data/
    ├── README.md                # 能力的当前完整需求基线
    └── changes/
        ├── README.md            # 变更状态与文档索引
        └── PRD-<编号>-<主题>.md   # 有独立交付需求时创建
```

新增能力使用稳定的英文目录名，如 `stock-analysis/`。每个能力的 `README.md` 记录目标与范围、使用流程、业务规则、输入输出、异常行为、验收标准和关联文档。

## 需求粒度与维护流程

- 小型字段、文案或规则补充，直接更新能力主文档；无需为每次修改单独创建文档。
- 可独立评审和交付的需求，在所属能力的 `changes/` 下创建一份文档。跨 API、任务、Worker 和数据库的同一用户目标仍使用一份需求文档，链接到相应技术方案。
- 编号使用产品目录内递增且不重复的 `PRD-001`、`PRD-002` 等；创建前检查已有编号。文件名示例：`PRD-001-history-backfill.md`。
- 变更文档记录编号、状态、所属能力、背景与目标、范围、业务流程与规则、异常行为、验收标准和关联方案。状态依次为草稿、待评审、已确认、开发中、已验收；取消的需求标记已取消。
- 需求确认后，将确认的规则合并到能力主文档，并标注尚未交付的部分；交付后更新实现状态和验收证据。变更文档保留历史，不作为当前规则的唯一入口。
- 跨能力需求归入主要用户目标所属能力，其他能力通过索引引用同一文档；分别同步各能力主文档。

## 与其他文档的关系

| 位置 | 维护内容 |
|---|---|
| [架构设计](../architecture/README.md) | 产品整体范围、能力关系、技术边界和数据模型 |
| `docs/product/` | 各能力的业务需求、用户行为、验收标准与变更历史 |
| `docs/development/` | 实现方案、协议和实际验收证据 |
| `.trae/documents/` | 开发计划和评审过程资料 |

影响产品整体范围、数据口径或验收门禁的需求，同步更新相关架构文档。字段精度、数据库结构和 Worker 协议通过链接引用其权威文档，避免多处重复维护。
